왼쪽은 실제로 붙을 화면, 오른쪽은 그 화면의 각 요소가 부르는 API다. 번호가 좌우를 잇는다 — 어느 쪽이든 올려두면 짝이 같이 켜진다.

인증

고객 API는 회원 Authorization: Bearer. 관리자 API(/admin/*)는 관리자 토큰이다 — 회원 토큰으로 부르면 401. 환불 실행·수동 완료·발표 정정은 super_admin 관리자만 된다(그 외 403).

응답 봉투

단건은 { result, data }, 목록은 { result, data: { total, list } }. 이 문서의 → 는 data 안쪽만 적었다. 204 는 본문이 없다.

상태 문구 · 언어

상태는 코드(deliveryStage)로 분기하고 화면에는 서버가 준 …Label 을 그대로 쓴다. 헤더 Accept-Language: ko | en | zh-TW. 비우거나 모르는 값이면 한국어.

금액

통화는 NT$, 전부 정수. 합계(totalAmount)는 이미 할인이 빠진 값이라 프론트가 다시 빼지 않는다.

필드 표기

key 필수 · key? 선택(응답에선 null 가능) · key* 조건부 필수(조건은 카드 본문) · // ① // ② 택1. 정의하지 않은 키를 보내면 400 이다(전역 forbidNonWhitelisted).

변경 표기

기준은 payment-ui-api-map.html(결제 1차, 2026-11-04). new 새 API · updated 필드가 늘어난 API. 라벨이 없으면 예전 그대로다. 03 의 3~5번, 05 의 5~7번, 07·08 은 2026-11-25 에 더해졌다.

Swagger

DEV api-dev.seoulmoment.com.tw/docs · PROD api.seoulmoment.com.tw/docs. 2026-11-25 에 더해진 API 의 링크는 DEV 배포 뒤에 열린다 (PROD 는 main 뒤).

실측

예시 값은 코드와 통합 테스트(test/order.fulfillment.spec.ts)에서 가져왔다. 발표 作廢·折讓 은 ECPay stage 에 실제로 호출해 확인했고, LINE Pay 환불과 관리자 API 는 DEV 실측 전이다.

버튼은 상세 응답의 canRequestCancel 이 true 일 때 보인다 — 결제 완료 주문이면 24시간이 지나도, 한국 발주·해외배송 중이어도, 수령한 뒤에도 true 다(법정 계약해제권). 숨기는 조건을 프론트에서 따로 만들지 않는다. isQuickCancelPeriod 는 안내 문구만 바꾼다(24시간 안이면 “快速取消”, 지나면 “解除契約”). 이 API 는 접수만 하고 돈을 돌려주지 않는다 — 환불은 관리자가 확인 후 진행하고 그 상태가 4번에 뜬다. 204 라 본문이 없으니 성공하면 상세를 다시 부른다. 두 번 눌러도 204 이고 처음 접수 시각이 유지된다.

4환불 진행 상태 · 발표 정정new
같은 응답refund · invoice.adjustStatus

refund 가 null 이면 환불이 아직 시작되지 않은 것이다(접수만 된 상태 — “申請已受理” 로 보여준다). REQUESTED·PROCESSING 은 “退款處理中”, COMPLETED 는 “已退款”, FAILED 는 실패라고 쓰지 말고 “處理中，客服確認中” 정도로 둔다(관리자가 다른 방법으로 돌려준다). 환불이 끝나면 주문 status 가 CANCELED 로 바뀌고 invoice.adjustStatus 가 VOIDED(作廢) 또는 ALLOWANCED(折讓)가 된다.

{ refund?: { status: "REQUESTED", amount: 3880, requestedAt: "2026-11-25T06:02:00Z", completedAt?: null }, invoice?: { …, adjustStatus: "NONE" } }
5대만 국내 운송장 · 수령 시각new
같은 응답localCarrier · localTrackingNo · deliveredAt

관리자가 입력하기 전에는 셋 다 null 이라 블록을 숨긴다. 국제운송장·수입신고번호·통관 상태는 고객 응답에 내려가지 않는다. deliveredAt 은 배송 완료(6단계)일 때만 있다.

주의 — “24시간 간편취소”는 서비스 안내일 뿐 신청 가능 기한이 아니다. isQuickCancelPeriod: false 여도 canRequestCancel 이 true 면 버튼을 그대로 둔다. 고객 고지 문구(약관)는 법무 검토 후 확정이라 위 중문 문구는 명세의 추천안이다.

등록은 orderIds 만 필수이고 나머지는 아는 것부터 채운다. 수정은 보낸 필드만 바뀐다 — 글자 필드는 빈 문자열이나 null, 날짜 필드는 null 을 보내면 지워진다. orderIds 를 보내면 실린 주문이 통째로 교체되니 추가할 때도 기존 ID 를 같이 보낸다. 통관 상태를 바꿔도 주문의 배송 단계는 안 바뀐다 — 단계는 05 의 5번 API 로 따로 바꾼다. 저장할 때마다 실린 주문의 작업 이력에 한 줄이 남는다.

최근순. 칩은 status 쿼리로 건다. 행 버튼은 두 상태를 보고 정한다 — 환불 REQUESTED + isManual → “완료 입력”(/refund/complete), 환불 FAILED·PROCESSING → “환불 재시도”(/refund), 환불 COMPLETED + 정정 FAILED·PENDING → “발표 정정 재시도”(/invoice-adjust). 버튼이 부르는 API 는 05 의 6번과 같다. 발표가 발행된 적이 없으면 invoiceStatus 가 PENDING·FAILED 이고 정정은 NONE 이다(“未開立”).

←Query
page?: 1 count?: 10 status?: "FAILED"
→Response 200
{ total: 4, list: [{ refundId: 7, orderId: 481, orderNumber?: "SM-20261123-000481", recipientName?: "李佳蓉", method: "LINE_PAY", amount: 3880, status: "COMPLETED", isManual: false, pgRefundId?, attemptCount, failureCode?, failureMessage?, cancellationRequestedAt?, requestedAt, completedAt?, invoiceAdjustment?: { invoiceStatus: "ISSUED", adjustStatus: "VOIDED", … } }] }
관리자 Bearer 필수count ≤ 100status: REQUESTED · PROCESSING · COMPLETED · FAILEDadjustStatus: NONE · PENDING · VOIDED · ALLOWANCED · FAILED
주의 — 환불은 전액만 된다(부분 환불·상품별 환불 없음). ECPay 결제는 서버가 PG 환불을 보내지 않으므로 “완료 입력”을 누르기 전에 실제로 돈을 돌려줬는지가 운영 책임이다. PROCESSING(결과 미확인)은 수동 완료가 막혀 있다(409) — 재시도로 결과부터 확인해야 이중 환불이 안 난다. 결제 후 처리 실패(FAILED) 주문은 04 목록에 안 나와서 주문 ID 로 직접 환불을 시작해야 한다.

호출 순서 한 장

고객이 주문서를 보고 → 주문이 쌓인 뒤 → 관리자가 24시간 뒤에 발주하기까지, 실제로 나가는 요청만.

POST /user/order

탭·기간을 바꿀 때마다 같은 목록 API. 한 건을 열면 상세(배송 단계·할인 스냅샷).

KPI 는 1분 간격, 목록은 칩·검색·페이지가 바뀔 때. 남은 시간은 서버 값을 쓴다.

관리자 — 드로어 · 발주

행 클릭 때 상세 1회. canStartPurchase 가 true 면 발주(204) → 상세를 다시 불러 상태를 갱신.

06

관리자 — 통관·물류 · 배송 단계

묶음을 등록·수정하고, 실제 물류가 움직였을 때 단계를 따로 바꾼다. 둘은 서로를 바꾸지 않는다.

POST /admin/shipment PATCH /admin/shipment/{id} POST /admin/order/delivery-stage PATCH /admin/order/{id}/local-delivery
07

고객 — 취소·계약해제 신청

접수만 한다(204). 관리자 KPI “취소 요청”이 올라가고 그 주문의 발주가 막힌다. 고객은 상세를 다시 불러 접수 시각을 본다.

POST /user/order/{id}/cancel-request GET /user/order/{id}
08

관리자 — 환불 → 발표 정정

LINE Pay 는 한 번에 끝나고, ECPay 는 직접 돌려준 뒤 완료를 입력한다. 환불이 끝나면 발표 정정이 이어서 돌고, 정정만 실패하면 정정만 다시 누른다.

POST /admin/order/{id}/refund POST /admin/order/{id}/refund/complete POST /admin/order/{id}/invoice-adjust GET /admin/refund
09

운영 — 할인 스위치

sandbox 확인 뒤 켠다. 켠 직후부터 01 의 응답이 바뀐다.

GET /admin/shipping/policy PATCH /admin/shipping/policy
전체 스펙은 Swagger(/docs)에서 본다. 이 문서의 값은 커밋 6e6ac66 의 코드와 테스트(test/order.fulfillment.spec.ts 등)에서 가져왔고, 07·08 과 취소 신청·환불 필드는 2026-11-25 에 더해졌다(new 표시). ECPay 발표 作廢·折讓 은 stage 상점에서 실제 호출로 확인했고, LINE Pay 환불은 sandbox 승인 결제가 없어 테스트(모의 응답)로만 확인했다. 아직 없는 것: 부분 환불, ECPay 카드 자동 환불(DoAction), 반품 회수·검수·재입고, 고객 알림.
